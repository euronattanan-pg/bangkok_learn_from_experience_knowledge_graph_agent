# Local learning-from-experience PoC

A local-only web app for reviewing a transcript against the included LFE questionnaire, explicitly approving it, and writing a case to an existing Neo4j database. The backend also supports a read-only case search. Thai, English, and mixed text are accepted; audio transcription is not included.

## Local Python setup (Windows)

In PowerShell, from this PoC checkout:

1. Run `python -m venv .venv`, then `.\.venv\Scripts\python.exe -m pip install -r requirements.txt`.
2. If `.env_dev` does not already exist here, run `Copy-Item .env.example .env_dev`. Open `.env_dev` in a local editor and set `NEO4J_URI`, `NEO4J_USERNAME`, `NEO4J_PASSWORD`, and, if needed, `NEO4J_DATABASE` (defaults to `neo4j`). **Rotate any password previously sent in chat and use the replacement. Never paste credentials into chat or commit this file.** Use the encrypted URI provided by the database service where available. Use dotenv syntax and single-quote values containing special characters such as `$` or `#`.
3. Stop any existing preview using port 8000, then run `.\.venv\Scripts\python.exe -m lfe.server --env-dev` and open <http://127.0.0.1:8000/>. Stop the app with Ctrl+C. This flag reads `.env_dev` only from the current directory; the app does not load it automatically. Process environment variables override file values, even when empty. Without the flag, only process environment variables are used.
4. Select **Check connection** in the app to run a read-only connectivity check. Before the first upload to a database, install the graph constraints with `.\.venv\Scripts\python.exe -m lfe.init_schema --env-dev --confirm-database <database-name>`, replacing the placeholder with the configured database name. This requires permission to create constraints. The command does not migrate or delete data.
5. Create a questionnaire, enter a title, submit it, open it from **Pending approval**, review and approve it, then use **Pending upload** to review all answers and explicitly choose **Upload to Neo4j**. The account needs write permission.

Mock uploads are disabled by default. Only after confirming `.env_dev` points to a dedicated test database, start the local app with `.\.venv\Scripts\python.exe -m lfe.server --env-dev --allow-mock-upload`. This is an operator assertion, not automatic detection of a test database: never use the flag against production. Approved mock cases remain explicitly uploaded one at a time and are marked `is_mock: true` in Neo4j. Restart without the flag to block mock uploads.

`.env_dev` is Git-ignored and excluded from the Docker build context. Leave the values empty to explore without a database; no connection is attempted until a check, search, or approved write is requested. The backend alone connects to Neo4j. The app binds to `127.0.0.1`; do not expose this unauthenticated PoC to a LAN or public network. Drafts are stored locally under `data`; protect the machine and avoid inappropriate sensitive transcripts.

If a previous background preview occupies port 8000, run `Get-NetTCPConnection -LocalPort 8000 -State Listen` to identify its owning PID. Inspect that PID locally (for example, `Get-CimInstance Win32_Process -Filter "ProcessId = <PID>"`) and use `Stop-Process -Id <PID>` only after confirming it is the LFE preview.

## Docker alternative

With Docker Desktop installed, use `docker compose --env-file .env_dev up --build` and stop with `docker compose --env-file .env_dev down`. Docker stores drafts in a separate `lfe_data` volume, not the Python preview's local data. The file's values are passed to the backend container; the file itself is excluded from the image. Process environment variables can override Compose file values.

## Workflow and current limitations

1. Paste a transcript and create a draft. The model adapter is deliberately in **manual mode**: it does not call Copilot or infer answers. Every answer starts as null. Enter answers and optional transcript evidence; blanks remain null.
   Alternatively, select a prepared mock case and load it for review. Loading is temporary and does not create a draft until **Save review** is selected. Sample drafts are marked as mock; missing values remain blank and mock uploads require explicit test-database mode.
2. Save the review and submit it for approval. An LFE title is required. Use **Preview graph mapping** on a saved review to inspect the proposed separated entities before approving; the preview does not read or change Neo4j. Review a submitted case from **Pending approval** before explicitly approving it. Saving edits to a pending or approved case returns it to draft and requires resubmission. Only an approved snapshot can be uploaded. The 18 included questions are numbered sequentially, with date/time as question 3 and safety/product quality impact as question 4; related answers are grouped under their question. Excluded questions are not captured. Cause confirmation is an optional reviewer-supplied distinction; an unconfirmed cause is not promoted to a ConfirmedCause node.
3. **Pending upload** shows approved case details and an explicit per-case upload control. **Approved history** shows approved cases awaiting upload, uploaded cases, upload failures, mock cases and cases returned to draft. The backend validates values and writes a case and related nodes in one Neo4j transaction. If an upload fails or the app is interrupted, its outcome may be unknown; the unchanged approved snapshot can be retried, but edits are locked after an upload attempt. A confirmed duplicate title is rolled back and returned to draft for correction and reapproval. Attachment links are stored as text, not uploaded. Drafts and status persist locally.
4. Search saved cases. This is a fixed, parameterized, read-only keyword query with up to 20 results and case IDs, not semantic Q&A. It does not accept or execute model-generated Cypher. It may miss matches, especially in unsegmented Thai. The response is a simple list, not the as-yet unspecified answer template.

The **Audit trail** records lifecycle transitions, rejected actions, upload outcomes and UTC timestamps in the local SQLite store, without transcripts or credentials. The app has no authenticated user identity, so the actor is shown as unknown. The screen shows the latest 200 events; older events remain in the database. Existing cases are recorded as legacy imports rather than inventing past audit events. SQLite and Neo4j cannot be committed together; an interrupted upload is flagged as having an unknown outcome.

### Graph identity and reuse

LFE titles are unique after Unicode NFKC normalization, case folding, and whitespace normalization. Drafts are checked locally under a SQLite write lock; Neo4j also enforces unique case IDs and normalized title keys, including across app instances. Retrying the same case ID is idempotent. Local historical uploads marked **unverified after database reset** are retained for audit but do not reserve a title; the graph constraint remains authoritative for the target database. A database reset and local audit updates are separate operations and cannot be atomic.

Projects, products, lines, materials and suppliers are shared by exact normalized name within the database. Machines are shared only when the exact normalized machine name and line name match. Components are individual nodes shared only for the same normalized component, machine and line. Each component is also linked to its machine when exactly one machine is identified; with multiple machines, no assignment is guessed. Without unambiguous machine and line context, components remain case-specific. These are **reported-name references**, not verified master-data identities: no synonyms, SKU equivalence, site, supplier relationship, or physical asset identity is inferred. If identical names denote different entities, qualify the names in the questionnaire (for example with the site) before approval; there is no interactive entity-resolution mechanism. Product status/details are kept on the case-to-product relationship when there is one product; otherwise they remain on the case.

In the questionnaire, separate multiple project, product, line, machine, material or supplier names with semicolons or new lines. Components also split on commas and the word `and`; attachment names also split on commas. Separate distinct actions with semicolons or new lines. Double-quote a single name or action containing one of its delimiters, and double an embedded quote. Review the proposed mapping before approval: delimiters are not semantic understanding. The original answers and evidence are retained on the case or evidence nodes. Issues, defect descriptions, causes, impact details and verification are narrative occurrences and are not split on punctuation. Multiple attachment names are separate case-specific evidence nodes; a single link is not assigned to one name when the association is unknown. A case-level effectiveness answer is not attributed to every individual action when several actions are listed.

Node display names are title-cased and recognized acronyms such as LFE, SKU, RCA, EO, PLC, VAT, NPI and CTMZ-HU remain uppercase; the acronym list is maintained in `lfe/schema.py`. Original questionnaire text remains unchanged. Neo4j labels retain PascalCase and property keys remain snake_case.

**Existing graph migration:** databases containing cases created with the previous mapping, including combined component nodes, require a reviewed migration before using the new mapping. Local history created before mapping versions were recorded shows the upload's graph version as unverified, not upgraded. The new mapping requires component-node and component-link uniqueness constraints and rejects uploads while any older case is present. There is no automatic migration or cleanup command. Do not mix old and new app versions against the same database. Existing shared node display names are not overwritten on later matches. Installing constraints alone does not migrate old cases.

The project has no existing graph schema artifact or SDK configuration in this checkout. The mapping reflects the supplied questionnaire and node names; it should be checked against the authoritative latest chart before production use. Unknown cause status, action type, and other unavailable values are not invented. Relationships link each relevant entity directly to the case, rather than asserting relationships between entities that the questionnaire does not establish.

`lfe/model.py` isolates extraction and answer formatting for a future model adapter. No Copilot SDK integration or authentication is currently configured, and no AI requests are made. A future adapter must preserve the approval gate, validate model output, keep authentication outside the browser and image, and constrain query generation before any backend execution. This PoC uses one synchronous app service rather than a separate worker; there are no background model jobs.

## Tests

Run `.\.venv\Scripts\python.exe -m unittest discover -s tests -v`. Tests use mocked connections and require neither credentials nor a Neo4j connection. A live database is needed to exercise actual writes.
